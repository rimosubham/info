PILLAR 01 · WHAT WE DO

The problem we exist to solve.

Every business runs on a stack of SaaS tools. Those tools change pricing constantly. There is no single place to see what's changed, what's about to change, or what it's costing you year over year. We built the place.

01

Pricing pages change quietly.

SaaS vendors don't email when they raise prices — they update the page, ship a release note nobody reads, and rely on the fact that 90% of customers won't notice for months. Of the 14,392 changes we've logged, fewer than 8% were announced publicly before they shipped.

02

Stacks are fragmented.

The average freelancer runs 8 tools. The average SMB runs 14. People-ops leads run 9. That's 9 different vendors, 9 different roadmaps, 9 different surprise emails — and no human has the time to monitor all of them. We do it for you, in one ledger.

03

Forecasting is opaque.

Finance teams plan 12 months ahead. SaaS pricing changes within 30. Without forward visibility, every renewal is a budget surprise. PricePulse is the first system to forecast pricing changes 60–180 days early using public, auditable signals.

PILLAR 02 · HOW WE DO IT

The 9-stage pipeline.

Every tool in The Ledger flows through this pipeline every day. Every stage is automated, monitored, and human-audited. Below is the actual sequence — no marketing fluff, no hidden steps.

01
DISCOVERY · ONBOARDING

Tool discovery and onboarding.

New tools enter The Ledger via four channels: a Product Hunt scraper that catches launches within 24 hours, a Crunchbase feed for funded SaaS, manual editorial curation for niche categories, and the public "Request a tool" form. Every candidate is verified, classified by scrape tier, fitted with an initial parser, then run through a 14-day calibration window before going live.

RATE~214 tools added per month
CALIBRATION14 days before publish
SOURCES4 discovery channels
02
SCRAPING · 3-TIER

Three-tier daily scraping.

Pricing pages aren't built the same way. Roughly 40% are static HTML we scrape with httpx (~0.5s per page). 45% require JavaScript rendering via headless Chrome on Playwright (~5–8s per page). The remaining 15% sit behind Cloudflare, DataDome, or PerimeterX and route through residential proxies and Web Unlocker services. Jobs are distributed across an 18-hour window so we don't pattern-match like a bot.

TIER 12,338 tools · static HTML
TIER 22,631 tools · Playwright
TIER 3878 tools · Web Unlocker
03
SNAPSHOT · DIFF

Snapshot & intelligent diffing.

Every scraped page is normalised to clean markdown via Trafilatura, then hashed and compared against yesterday's snapshot. If the hash matches, we skip the rest of the pipeline — no LLM call, no human review, no cost. This single optimisation cuts our processing budget by ~85% on stable tools while still capturing every real change.

SNAPSHOTS5,847/day to R2 storage
CHANGE RATE~12% of tools change daily
RETENTION90 days hot, archived after
04
AI EXTRACTION · LLM

LLM-based structured extraction.

Pages that changed are passed to a small, fast LLM (Claude Haiku or GPT-4o-mini) with a strict JSON schema prompt. The model extracts plan tiers, prices, billing units, included quotas, and feature deltas — all in a single round trip. We pay roughly $0.001 per page change. Because we only call the LLM on actual changes, total monthly LLM cost stays under $600 for 5,847 tools.

// Extraction schema — strictly enforced { "plans": [{ "name": string, "monthly_price_usd": number | null, "annual_price_usd": number | null, "billing_unit": "per_seat" | "flat" | "usage" | "contact_tier", "included_quota": { /* category-specific */ }, "is_enterprise_gated": boolean }], "pricing_model_changed": boolean, "notes": string }
05
VALIDATION · GUARDRAILS

Schema validation & hallucination guards.

LLM output is validated by a Pydantic schema, then run through a substring check — every extracted price must literally appear in the source HTML. This single rule catches ~80% of LLM hallucinations on its own. Anything that fails validation is re-queued with a different prompt; if it fails three times, it's flagged for human review.

PASS RATE96.4% on first attempt
SUBSTRING CHECKCatches 80% of hallucinations
RETRIESMax 3 before human queue
06
HUMAN QA · IN-THE-LOOP

Human-in-the-loop verification.

Not all changes auto-publish. Anything that looks suspicious — a >25% price swing, a plan removal, a first extraction for a new tool, an LLM confidence below 0.85 — is routed to our editorial dashboard. A human reviewer (currently a senior VA, soon two) approves, edits, or rejects within 24 hours. Decisions feed back into the LLM prompt library, so the system gets better every week.

QUEUE RATE~3.6% of changes flagged
REVIEW SLA<24 hours
LEARNING LOOPDecisions retrain weekly
07
STORAGE · APPEND-ONLY

The price_events ledger.

Verified changes land in our append-only price_events table — a Postgres database that has never been edited or pruned, only grown. Every change has a date, a source HTML snapshot in R2, an author (LLM or human), and a confidence score. This is the single most valuable asset on the platform. It's backed up nightly to two separate cloud providers and snapshotted weekly to cold storage.

FORECASTING · ML ENSEMBLE

The forecast engine.

Once data is verified, it feeds a four-signal ensemble model that predicts the probability of a hike in the next 30/60/90/180 days. The model combines time-series analysis on pricing cadence, NLP on financial filings and earnings calls, behavioural pattern matching on leadership signals, and competitive cluster analysis. The full architecture is detailed in the next section.

THE FORECAST ENGINE · DEEP DIVE

Four signals.
One confidence score.

Our ensemble model doesn't predict pricing by magic, intuition, or trend-line extrapolation. It runs four independent signal streams every night, weighs them via a learned ensemble, and produces a single probability — validated quarterly against the historical events table.

Not magic.
Just math.

Each of the four streams below produces an independent score from 0 to 1. The ensemble combines them with weights learned from 14,392 historical events.

The model has flagged 73% of major price increases more than 60 days before they shipped. It misses the rest — usually because the pricing change was triggered by an external event (acquisition, ToS lawsuit, regulatory shift) the model has no visibility into. We publish the misses too, in our quarterly methodology updates.

Every prediction on every tool page links back to the underlying signal data, so you can see exactly why we think what we think — and decide for yourself if our reasoning holds up.

METHODOLOGY · THE LINES WE WON'T CROSS

What we do. What we don't.

A pricing-data company has many ways to cheat — fabricate prices, scrape behind logins, manipulate forecasts to favour partners, or quietly correlate user data. We won't. Here's the exact list.

✓ What we do

  • Scrape only public pricing pages. If a vendor publishes a price, we read it. If they hide it behind sales, we mark it as "Contact Sales" and move on.
  • Validate every extraction. Substring check, schema check, confidence score — and a human reviews anything suspicious before publish.
  • Publish historical data openly. Every event in the price_events ledger has a public URL with the source HTML snapshot.
  • Disclose our methodology. Pipeline architecture, signal weights, error rates — published quarterly, updated when we change anything.
  • Treat sponsored content as walled. Our tool detail pages contain zero paid placements. Sponsorships live only on listicles and comparisons, clearly marked.

✕ What we don't

  • Scrape behind authentication. No fake accounts, no impersonation, no scraping anything that requires a login or violates a vendor's reasonable expectations.
  • Use AI to fabricate prices. If our extraction can't find a price in source HTML, we leave the field null. We never let the LLM "infer" a number.
  • Tilt forecasts to favour anyone. Sponsored vendors don't get softer predictions. Our affiliate links don't bend the model. Predictions are blind to commercial relationships.
  • Sell user data. We don't sell, share, or monetise the watchlists or alert preferences of our users — full stop.
  • Auto-publish without QA gates. Anything flagged by our validation layer waits for human review. Speed never overrides accuracy.

INFRASTRUCTURE · TRANSPARENT BY DEFAULT

The stack behind the ledger.

If you've made it this far, here's the boring stuff. Our infrastructure is intentionally simple — fewer moving parts means fewer ways to break.

SCRAPING

Playwright + ScrapingBee

Headless Chrome on a worker pool plus Web Unlocker for protected sites. ~5,847 jobs/day across three tiers.

EXTRACTION

Claude Haiku · GPT-4o-mini

Small fast LLMs running JSON-schema-constrained prompts. ~$0.001 per change extracted.

STORAGE

Postgres + Cloudflare R2

Append-only price_events table on Postgres, raw HTML snapshots on R2 (zero egress). Backed up nightly.

QUEUE

Redis + Celery

Distributed job queue with retry, exponential backoff, and dead-letter handling for failed scrapes.

FORECASTING

Python ensemble

scikit-learn + custom NLP models on Hugging Face transformers. Retrained quarterly on new events.

FRONTEND

Next.js + ISR

Pre-rendered tool pages refreshed every 6 hours via Incremental Static Regeneration. CDN'd via Cloudflare.

SEARCH

Meilisearch

Self-hosted full-text search across 5,847 tools and 14,392 events. Typo-tolerant, sub-50ms response.

ALERTS

Resend + Slack API

Transactional email + Slack incoming-webhook fanout. Median time from change to notification: under 2 min.
